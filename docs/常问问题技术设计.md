# 常问问题技术设计

更新：2026-10-15。本文档说明基于大语言模型与向量聚类的“常问问题（Frequent Questions）”自动化发现与推荐系统的技术架构、数据结构、语义聚类流程及关键防误判机制。

## 1. 业务目标与设计原则

- **智能提炼与提问引导**：从用户的历史问答流中，自动提炼高频提问意图，生成代表性问题，在开场白或输入建议中展示，降低用户提问门槛。
- **租户与数据范围严格隔离**：常问问题基于 `user_id` 与绑定数据源指纹（`scope_key = SHA256(sorted(source_ids))`）严格隔离，保证在不同业务空间或数据集合下，推荐的问题完全贴合当前数据上下文。
- **保守匹配策略（Conservative Matching）**：宁可错失归组生成新问题，坚决杜绝把不同口径、不同筛选边界或不同时间维度的提问错误合并。
- **时间上下文绝对化比对**：彻底杜绝“相对时间（如'本月'、'今年'、'昨天'）”导致的误合并。2026年10月的“本月销量”与2026年11月的“本月销量”即使字面完全相同，属于不同时间跨度，不可合并。
- **异步解耦与背压控制**：问答主链路记录待处理队列，统一 worker 的 frequent 角色顺序执行向量嵌入与 LLM 语义裁决，也支持独立常问 worker 入口。Celery 适配器仅调度 Agent 运行。

## 2. 总体架构与数据流

```text
[ 用户在对话中发送问题 ]
        │
        ▼ (主事务同步执行)
[ enqueue 阶段: 写入 question_records (status='pending') ]
        │
        ▼ (异步后台消费)
[ 1. 过滤与标准化 ]
        │ 剔除纯寒暄、无意义追问或空文本
        ▼
[ 2. 向量嵌入生成 (Embedding) ]
        │ 调用配置的 Embedding 模型 (如 text-embedding-v3 / bge-m3)
        ▼
[ 3. 余弦相似度粗筛 (Top-K Candidates) ]
        │ 从同 user_id + scope_key 的 question_groups 中按 cosine 选出 Top 3
        ▼
[ 4. LLM 结构化精确裁决 (LLM Judge) ]
        │ Prompt 注入双方各自的绝对时间上下文
        │ 返回: {"eligible": bool, "matched_group_id": string | null}
        ├─ eligible=false ──> status = 'skipped'
        ├─ matched_group_id != null ──> 关联到现有 QuestionGroup, status = 'completed'
        └─ matched_group_id == null ──> 创建新 QuestionGroup, status = 'completed'
        ▼
[ 前端展示聚合 ]
   按 group 统计 completed 记录数，>= threshold 时暴露给前端推荐
```

## 3. 数据模型设计

由 `app/models/frequent.py` 提供支撑：

### 3.1 意图分组表：question_groups

| 字段名 | 类型 | 说明 | 约束 |
| :--- | :--- | :--- | :--- |
| `id` | `VARCHAR(36)` | 分组主键 UUID | PK |
| `user_id` | `VARCHAR(36)` | 用户 ID | FK -> `users.id` (CASCADE) |
| `scope_key` | `VARCHAR(64)` | 数据源集合的 SHA256 签名 | NOT NULL |
| `representative_question`| `TEXT` | 该组的标准代表性问题文本 | NOT NULL |
| `representative_asked_at`| `DATETIME` | 代表问题发生的时间（用于基准时间计算） | NOT NULL |
| `embedding` | `JSON` | 代表问题的向量浮点数组 | NOT NULL |
| `embedding_profile` | `VARCHAR(64)` | 生成该向量的模型标识/Profile | NOT NULL |

- **索引**：`Index('ix_question_groups_user_scope', 'user_id', 'scope_key')`。

### 3.2 待处理记录表：question_records

| 字段名 | 类型 | 说明 | 约束 |
| :--- | :--- | :--- | :--- |
| `message_id` | `VARCHAR(36)` | 关联的用户消息 ID | PK，FK -> `messages.id` (CASCADE) |
| `user_id` | `VARCHAR(36)` | 用户 ID | FK -> `users.id` (CASCADE) |
| `scope_key` | `VARCHAR(64)` | 数据源范围哈希 | NOT NULL |
| `source_ids` | `JSON` | 当时关联的数据源 ID 列表 | NOT NULL |
| `group_id` | `VARCHAR(36)` | 归属的意图分组 ID | 可空，FK -> `question_groups.id` (SET NULL) |
| `normalized_text` | `TEXT` | 清理空白后的标准化问题正文 | NOT NULL |
| `status` | `VARCHAR(20)` | 处理流水状态 | 默认 `'pending'` |
| `attempts` | `INTEGER` | 重试次数 | 默认 0 |
| `error_code` | `VARCHAR(80)` | 失败/跳过原因代码 | 默认空字符串 |
| `created_at` | `DATETIME` | 记录入队时间 | 默认当前时间 |

- **状态约束**：`CHECK (status IN ('pending', 'processing', 'completed', 'skipped', 'failed'))`。
- **索引**：
  - `(user_id, scope_key, status)`：扫描用户作用域内未处理任务。
  - `(status, created_at)`：后台 Worker 调度队列消费。

## 4. 关键算法与判决机制

### 4.1 作用域签名（Scope Key）

不同业务空间绑定的数据源集合各异。系统计算确定性指纹：
```python
def scope_key(source_ids=()):
    value = sorted(set(source_ids))
    return hashlib.sha256(json.dumps(value, ensure_ascii=False, separators=(',', ':')).encode()).hexdigest()
```
即使同一用户在不同业务空间提问，如果数据源范围不同，其问题组完全独立，绝不混淆。

### 4.2 向量粗筛（Embedding Cosine Filter）

从同作用域内已有 completed 记录的问题组中，按余弦相似度选取 Top 3 候选交给模型判决，不设置相似度下限。无相对时间表达的完全相同问题可以直接复用已有分组。若嵌入模型 Profile 发生变更，任务回到 pending 并标记 `embedding_profile_changed`，该用户的消费暂停；不会自动重算旧组，需要用户重置常问统计。

### 4.3 时间绝对化与 LLM 精确裁决（Two-Stage Judge）

模型使用 Temperature=0 且约束 JSON Schema 输出：
```json
{
  "eligible": true,
  "matched_group_id": "group-uuid-or-null"
}
```

系统内置两阶段防误合并规则：
1. **资格判定 (`eligible`)**：
   - 必须是可独立理解的信息诉求。
   - 依赖上文的代词或省略追问（如“那上海呢”、“再画个图”、“同比呢”）直接置为 `eligible=false`，不进入常问问题池。
2. **意图匹配 (`matched_group_id`)**：
   - 核心对象、指标、数值边界、排序条件（Top 5 vs Top 10）有任何差异，必须返回 `null`。
   - **时间基准绝对化**：新问题与每个候选问题在传入 Prompt 时，均附带各自被提问时的绝对时间上下文：
     ```json
     {
       "question": "本月营收是多少",
       "asked_at": "2026-10-15T16:00:00+08:00",
       "time_context": {"year": 2026, "month": 10, "local_date": "2026-10-15", "yesterday": "2026-10-14"}
     }
     ```
     模型必须首先将相对时间换算为绝对区间。若提问时间在 10 月，而候选在 9 月，即便两句字面同为“本月营收”，裁决器亦必须判定为不匹配并返回 `null`。

## 5. 聚合与对外接口

### 5.1 获取常问问题列表

- **路径**：`GET /api/frequent-questions?workspace_id=workspace-id`；也支持重复的 `source_ids` 查询参数，如 `?source_ids=ds-1&source_ids=ds-2`。
- **逻辑**：
  1. 校验当前用户与数据源合法性。
  2. 统计当前 `scope_key` 下每个 `QuestionGroup` 关联的 `completed` 记录数（`COUNT(message_id)`）。
  3. 仅保留 `count >= threshold`（默认 3 次）的成熟分组。
  4. 按提问频次降序、最新提问时间降序排序，取 Top 10 返回。
- **返回结构**：
  ```json
  [
    {
      "id": "group-001",
      "question": "2026年三季度华东区销售额前三的商品",
      "count": 12,
      "last_asked_at": "2026-10-15T14:20:00Z"
    }
  ]
  ```

### 5.2 停用与清理

关闭“常问问题”功能时，调用 `skip_unfinished(db, user_id)`，将 pending 和 processing 任务更新为 `status='skipped', error_code='disabled'`。

嵌入模型 Profile 变化时，配置响应返回 `reset_required=true`。用户调用 `DELETE /api/frequent-questions` 重置该用户的记录和分组后，从新提问开始累计。嵌入向量和 Profile 字段仍属于当前功能，不属于已移除的文档索引。
