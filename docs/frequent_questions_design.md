# 常问问题功能方案（基础版）

状态：基础版已实现，自动化验证及阿里云真实模型样本、完整后端链路验收已通过。日期：2026-10-12。

实施与验证记录：[frequent_questions.md](validation/frequent_questions.md)。

适用环境：单机、小规模开发验证。数据库通过 Alembic 初始化，开发环境可按本方案重新初始化本功能的数据结构。

## 1. 功能目标

统计当前用户反复提出的相同问题，包括文字相同和表达不同但含义相同的问法。达到设置次数后，在聊天界面展示为可点击的常问问题。

核心功能：**问题归组、累计计数、达到阈值后展示**。

例如“2026 年北京代表处确认收入是多少？”和“北京代表处 2026 年确认了多少收入？”归为一组；改成上海、2025 年或者利润，则属于其他问题。

## 2. 系统架构

由聊天入口、常问 worker、应用数据库和常问列表接口构成，复用项目的 Embedding 与 LLM 调用能力。

```text
聊天界面 → 聊天入口 → 应用数据库
                         ├─ Message：聊天原文
                         ├─ question_records：待处理记录及归组结果
                         └─ question_groups：代表问题及向量

常问 worker → 读取待处理记录 → 精确匹配 / 向量召回 / LLM 判定
            → 将归组结果写回应用数据库

聊天界面 → 常问列表接口 → 按用户和资源范围聚合次数 → 返回常问列表
```

| 组件 | 职责 |
| --- | --- |
| 聊天入口 | 保存用户消息，并在同一事务中创建待处理记录 |
| 常问 worker | 单实例顺序处理，完成归组、状态更新和失败重试 |
| 匹配服务 | 文本归一化、精确匹配、向量排序和 LLM 等价判定 |
| 应用数据库 | 保存问题组、向量和提问记录，提供累计次数查询 |
| EmbeddingProvider | 生成问题向量 |
| LLM 服务 | 判断问题能否独立理解，以及是否与候选同义 |
| 常问列表接口 | 鉴权、按资源范围过滤、聚合计数和排序 |
| 前端常问入口 | 展示问题及次数，点击后填入输入框 |

问题向量以 JSON 数组保存在应用数据库中，在内存中计算余弦相似度。提问记录同时承担持久化待处理队列和计数依据的职责。统计在后台执行，聊天正常流式返回。

## 3. 业务规则

| 项目 | 规则 |
| --- | --- |
| 统计主体 | 每个用户独立统计，不跨用户合并或展示 |
| 业务范围 | 相同用户、相同知识库集合和数据源集合内比较 |
| 计数单位 | 每条符合条件且处理成功的用户消息记一次 |
| 重复提交 | 同一 message_id 只处理一次；用户再次发送形成新消息则再记一次 |
| 展示门槛 | 累计次数 >= threshold，默认 3 次 |
| 展示数量 | 最多 10 条，按次数降序、最近提问时间降序排列 |
| 代表问法 | 使用该组第一次确认的完整问题，不额外生成标准问法 |
| 功能关闭 | 不记录新提问、不展示常问；保留已有结果，重新开启后继续累计 |
| 统计触发 | 用户消息保存后开始，与 Agent 回答结果分开 |
| 点击常问 | 填入输入框，由用户提交后重新查询，不复用历史答案 |
| 删除会话 | 关联提问记录随消息删除；查询时重新聚合次数，无剩余记录的组不展示 |

业务范围使用 `scope_key`：对本次请求的 kb_ids 和 source_ids 分别排序、去重，再计算稳定标识。空集合也有独立范围。切换会话所属空间或空间配置变化时重新读取常问列表，不能混用不同数据源下的问题。聊天界面通过 `workspace_id` 由服务端解析当前来源，来源配置统一在业务空间管理页维护。

列表和后台处理均校验当前用户及资源所有权。资源不存在或已失效时不返回该范围的结果。

### 什么可以合并

| 提问 A | 提问 B | 处理 |
| --- | --- | --- |
| 2026 年北京代表处确认收入是多少？ | 北京代表处 2026 年确认了多少收入？ | 合并 |
| 北京代表处确认收入 | 上海代表处确认收入 | 不合并 |
| 2026 年确认收入 | 2025 年确认收入 | 不合并 |
| 销售额最高的 3 个型号 | 销量最高的 3 个型号 | 不合并 |
| 收入高于 3000 万 | 收入低于 3000 万 | 不合并 |
| 各产品线收入，用表格 | 各产品线收入，用柱状图 | 核心数据需求相同，可合并；保留首次问法 |
| 退款条件是什么 | 退款怎么操作 | 不合并 |

指标、对象、时间、筛选范围、否定含义、排序和 Top N 等关键条件不一致时不合并。无法确定时建立新组，接受少量漏合并，优先避免错误归组。

“你好”“谢谢”等纯寒暄不统计；“那上海呢”“再画个图”等必须依赖前文的追问暂不统计。基础版只处理能够独立理解的问题。

LLM 判定时提供新问题和代表问题各自的提问时间，时区统一为 Asia/Shanghai。“今年”与明确年份是否一致，由这次判定处理。包含“今年”“本月”“昨天”“最近”等相对时间表达时，即使文字相同也进入语义判定，避免跨时间误合并。复杂日期表达的识别效果通过验收样本验证。

## 4. 问题归组流程

采用 **保守文本归一化 → 精确匹配 → Embedding 召回 Top 3 → LLM 确认 → 保存归组**。

### 4.1 精确匹配

仅处理首尾空白、连续空白等明确的格式差异；不删除数字、否定词、单位或产品型号中的符号。

在当前用户和 scope 下，查找已处理记录中相同的归一化文本。符合精确匹配条件时直接复用其问题组，不调用模型。相对时间问题按上一节规则走语义判定。

### 4.2 向量召回

复用已有 `EmbeddingProvider`，将新问题转换为向量。读取该用户、该 scope 下仍有有效提问记录的问题组向量，计算余弦相似度，选出最接近的 3 组。

向量保存在问题组表中，采用 JSON 数组。

向量相似度用于排序候选，最终归组由 LLM 判定。

### 4.3 一次 LLM 判定

将新问题、提问时间和最多 3 个候选代表问题交给现有 LLM 服务，一次调用同时判断：

1. 新问题是否是可独立理解的信息需求。
2. 是否与某个候选表达完全相同的核心需求。

返回一个简单结构：

```json
{
  "eligible": true,
  "matched_group_id": null
}
```

- `matched_group_id` 为候选组 ID 字符串或 JSON null。
- `eligible=false`：跳过，不进入常问统计。
- `eligible=true` 且命中候选：加入该组。
- `eligible=true` 且未命中：建立新组，保存新问题及其向量。
- 首次没有任何候选时，仍做一次资格判断，避免把寒暄和省略追问建立为问题组。
- 输出格式错误、组 ID 不属于本次候选或模型调用失败：本次处理失败，不猜测归属。

提示词明确要求检查关键条件；问题文本仅作为待比较数据。多个候选难以区分时返回 null。每次与固定代表问法比较，保持问题组含义稳定。

非精确命中的单次处理最多调用一次 Embedding 和一次 LLM；调用失败后按重试规则重新处理。

## 5. 数据设计

Message 保存聊天原文；question_groups 和 question_records 保存常问统计数据，表结构通过 Alembic 定义。

| 表 | 核心字段 | 用途 |
| --- | --- | --- |
| `question_groups` | id、user_id、scope_key、representative_question、representative_asked_at、embedding、embedding_profile | 保存每类问题的代表问法和向量 |
| `question_records` | message_id、user_id、scope_key、资源 ID 集合、group_id（可空）、normalized_text、status、attempts、error_code | 一条新消息对应一条记录，同时用于待处理和计数 |

数据约束与查询规则：

- `question_records.message_id` 唯一并关联 Message，消息删除时级联删除记录。
- status 只保留 pending、processing、completed、skipped、failed。
- 保存用户、scope 和 status 的查询索引，以及 group_id 索引。
- 仅 completed 且 group_id 有值的记录参与计数，次数通过 `COUNT` 聚合，最近时间从关联 Message 取 `MAX(created_at)`。
- 代表问法是问题组自己的派生文本；删除部分会话后，如组内仍有其他记录，保留代表问法。无成员组不展示，开发重置时一并清理。
- 用户删除时级联清理其问题组和提问记录。

Embedding 模型在一次开发验证期间固定。通过 embedding_profile 检测向量是否来自相同模型；检测到模型变化时暂停该用户的常问处理并提示重置。重置范围为该用户的问题组和提问记录，保留聊天消息、知识库及业务数据；完成后从新提问开始统计。

## 6. 端到端流程与基本可靠性

```text
用户提交问题
  → 保存 Message
  → 开关开启时，同一数据库事务插入 pending 提问记录
  → 提交，正常执行聊天和流式回答

单个常问 worker 定期读取 pending 记录并顺序处理
  → 检查消息、用户、资源及开关
  → 精确匹配；未命中时执行向量召回和 LLM 判定
  → 在一个短事务中创建/选择问题组，写入 group_id 和最终状态

前端请求常问列表
  → 按用户及当前 scope 聚合 completed 记录
  → 过滤次数 >= threshold，排序后取前 10 条
```

运行与故障处理规则：

- 常问 worker 以单实例轻量进程运行，独立于文档处理队列，顺序处理提问记录。
- 提问记录随 Message 同事务落库，进程退出也不会丢掉待处理消息；worker 重启时将遗留 processing 记录恢复为 pending。
- 模型调用在 SQL 写事务之外执行，并设置超时。最多尝试 3 次，耗尽后标记 failed，记录简短错误；聊天照常工作。
- 完成时再次检查记录、消息和开关；已 completed 的记录直接跳过。新组写入和记录完成同事务提交，防止重试重复创建或计数。
- 功能关闭时，未完成记录处理为 skipped；重新开启不补算关闭期间或已跳过的问题。
- 页面进入、资源切换和回答完成后拉取列表；页面打开期间每 5 秒刷新，及时展示后台统计结果。

达到重试上限的记录标记为 failed，不参与计数。

## 7. 配置和界面

用户只需要两个设置：

| 配置 | 规则 |
| --- | --- |
| `is_enabled` | 是否启用自动常问 |
| `threshold` | 达到多少次展示，默认 3，必须为正整数 |

10 条上限、Top 3、重试次数作为后端常量。

新增 `GET /frequent-questions`，接收当前 kb_ids/source_ids，返回 `id、question、count、last_asked_at`。开关关闭或无符合条件的问题时返回空列表。

常问设置页提供开关与次数阈值；常问列表由真实统计结果生成，初始化为空。开场白配置中的问题用于手工推荐。

前端常问入口显示问题及次数；点击填入输入框，提交时使用当前资源并重新鉴权。

## 8. 实施步骤与模块职责

基础版本分三步完成：

| 步骤 | 实现内容 | 完成标准 |
| --- | --- | --- |
| 第一步：计数闭环 | 两张表、同事务记录、单 worker、精确匹配、累计查询接口 | 同一 message_id 不重复统计；相同完整问题达到 3 次可查询 |
| 第二步：不同问法归组 | SQL 存向量、内存 Top 3、一次 LLM 判定、基本失败重试 | 同义表达合并；指标、地域、年份等不同的问题分开 |
| 第三步：页面与验证 | 常问入口、开关和阈值设置、定期刷新及删除联动验证 | 可从提问到展示完整演示，故障不影响聊天 |

模块职责：

- `backend/app/services/frequent_service.py`：文本匹配、向量召回和 LLM 归组判定。
- `backend/app/application/chat.py`：保存消息时写入待处理记录。
- `backend/app/models/frequent.py` 与 Alembic 结构定义：问题组、提问记录及约束。
- `backend/app/workers/frequent.py`：顺序消费待处理记录和失败重试。
- 常问读取路由：鉴权、按范围查询和累计排序。
- `backend/app/schemas/config.py`、settings 和注册初始化配置：常问开关与阈值。
- 前端常问入口及配置弹窗：问题展示、点击填入和设置保存。

常问统计使用应用数据库，通过 EmbeddingProvider 和 LLM 服务完成模型调用。

## 9. 基础验收

用约 20～30 组人工确认样本进行开发验证。

| 验证项 | 预期结果 |
| --- | --- |
| 同一句完整问题主动发送 3 次 | 一个问题组，次数为 3，出现在列表 |
| 同一需求使用 3 种不同问法 | 归入同一组并达到展示门槛 |
| 指标/实体/年份/数值边界/否定/Top N 不同 | 不误合并 |
| 不同用户或不同资源范围 | 不混入候选和列表 |
| 寒暄、无法独立理解的追问 | 不计数 |
| 同一记录重试，或 worker 重启 | 不重复计数，遗留任务可继续处理 |
| 模型超时、返回无效组 ID | 不错误归组，聊天正常 |
| 删除相关会话 | 记录及列表次数相应减少，无成员组不展示 |
| 关闭后提问，再重新开启 | 关闭期间的问题不补算 |
| 更换 Embedding 模型 | 检测并停止混用；重置本功能数据后可以重新统计 |

同义匹配效果通过判定提示词、Embedding 配置和候选数进行校准，使用同一组样本复核结果。
