# 反馈管理与回复校对设计文档

- 状态：**基础版已实现，SQLite 本地迁移及功能验收通过**。
- 日期：2026-10-13。
- 依据：本次提供的四张截图、当前仓库实现及公开的人工反馈/标注产品文档。
- 目标版本：适用于现有单实例 RAG / SQL 问数平台的基础版。
- 实施范围：按本文建议默认值实施；本地 `admin` 账号已按用户确认授予反馈管理员权限。验收记录见 [反馈管理验收](validation/feedback.md)。

## 1. 目标与范围

将用户标记为有误的 AI 回复转为可追溯的反馈记录，供处理人员查看原始问题、回答及来源依据，登记核查结果并跟踪处理状态。

核心闭环：**用户报告错误 → 服务端保存原始问答快照 → 回复校对列表 → 人工核查与备注 → 已处理 / 重新打开**。

“已处理”表示核查工作已有结论，不保证模型、知识库或源数据已经修复。处理备注需要明确核查结论及后续动作。任何状态变更均不直接修改历史回答、不自动执行 SQL、不自动写入知识库或模型记忆。

### 1.1 本期交付范围

1. 聊天回答的“反馈错误”入口，反馈原因和补充说明。
2. 截图中的“反馈管理 → 回复校对”列表、搜索、状态筛选和分页。
3. 截图中的处理弹窗，包含原问题、AI 回复、处理状态和处理备注。
4. 必要的上下文、来源依据、处理人、处理时间、处理历史。
5. 服务端权限控制、提交去重、并发更新保护和自动化验收。

### 1.2 后续扩展

本期不引入点赞统计、自动聚类、优先级、分派、处理中状态、SLA、批量处理、附件、消息通知、自动修复及第三方标注平台。核查后的标准答案、评测集导入和回归评测作为后续质量改进链路设计，不能将未核实的用户反馈直接当作正确答案。

### 2.2 参考实践与本项目取舍

- LangSmith 将人工评价关联到具体运行或会话，提供审核队列、审核进度和基于输入/输出的审阅；本项目采用具体回答与运行记录的关联，以及集中处理列表。[官方说明](https://docs.langchain.com/langsmith/annotation-queues)
- Langfuse 的人工标注队列支持对运行轨迹、观察或会话记录评分及评论，并支持记录修正输出；本项目先保留用户错误原因和人工处理备注，修正答案进入后续阶段。[官方说明](https://langfuse.com/docs/evaluation/evaluation-methods/annotation-queues)
- Langfuse 将终端用户反馈和人工评价作为可通过 API/SDK 写入的质量信号；本项目区分“用户认为有误”和“人工已核查”，避免把反馈直接解释为已确认的模型错误。[官方说明](https://langfuse.com/faq/all/what-are-scores)

原始快照、乐观锁、两状态及权限方案是结合本项目提出的工程选择，不声称为上述产品的相同实现。本期在现有应用数据库中实现，无须部署 LangSmith 或 Langfuse。

| 现有代码 | 已有能力 | 设计影响 |
| --- | --- | --- |
| `frontend/src/components/layout/Sidebar.tsx` | 已有“反馈管理 / 回复校对（待开发）”占位 | 启用页面入口并按权限显示 |
| `frontend/src/components/chat/MessageItem.tsx` | 回答正文、引用、分析过程、复制及朗读 | 在助手回答操作区增加反馈入口，复用回答渲染能力 |
| `backend/app/models/conversation.py` | Conversation、Message；消息有用户、资源版本、正文、引用和工具结果 | 以 assistant message 为反馈对象，不能仅保存问题文字 |
| `backend/app/models/platform.py` | AgentRun 关联回答消息，保存输入与资源范围 | 用 `assistant_message_id` 查运行，用 `input_payload.user_message_id` 找原问题 |
| `backend/app/application/chat.py` | 同一请求创建问题、运行和回答占位消息 | 完成后有稳定消息 ID；运行中不能提交反馈 |
| `backend/app/api/sessions.py`、`api/runs.py` | 目前按当前用户隔离数据 | 跨用户校对必须新增独立权限；不能放宽原会话和运行接口 |
| `backend/app/models/user.py`、`security/auth.py` | 用户登录、JWT；User 没有管理员角色 | 角色识别是本功能前置改动，不能依据用户名推断管理员 |
| `backend/app/database.py` | SQLAlchemy 异步访问；支持 SQLite，其他部署可配置 PostgreSQL | 新表及查询兼容两种数据库，通过 Alembic 迁移 |

原问题优先使用运行中保存的明确消息关联，不使用“会话中最后一条用户消息”。后者在重新发送、多轮追问及运行恢复时可能配错答案。

## 4. 用户与权限

建议本期使用最小角色模型：给 User 新增 `role`，枚举 `user` / `feedback_admin`，默认 `user`。`feedback_admin` 只增加反馈校对能力，不自动获得管理模型配置、浏览所有会话或下载其他用户文档的权限。

管理员通过受控运维命令按用户 UUID 授予/撤销；公开注册、个人信息修改和前端传参不能授予角色。现有用户迁移后全部保持 `user`，首次管理员需在上线时明确配置；不按“管理员”这个用户名自动授权。API 每次从数据库读取当前角色，使撤权即时生效。

| 操作 | 普通用户 | 反馈管理员 |
| --- | --- | --- |
| 对自己的有效回答提交反馈 | 允许 | 允许 |
| 在聊天中查看自己反馈的状态 | 允许 | 允许 |
| 阅读反馈处理备注及审计历史 | 不允许；本期备注为内部字段 | 允许 |
| 进入回复校对列表、搜索用户、查看反馈快照 | 不允许 | 当前部署内全部反馈 |
| 更新状态与内部处理备注 | 不允许 | 允许 |
| 从反馈页访问原文档 / 执行记录 | 仍按原接口的所有权鉴权 | 不额外提权；仅能查看允许的快照 |

**权限假设：当前部署属于一个可信组织。** 现有业务空间属于用户私有资源，不是组织租户。全局反馈管理员可读取其他用户主动上报的业务内容，应明确告知提交者。若产品需要多个组织共享部署，必须先引入真实组织及成员范围；不能使用 `workspace_id` 冒充租户 ID。此项属于审核重点。

不存在或不属于当前用户的回答，提交接口统一返回 404；未登录返回 401；无校对权限访问管理接口返回 403。列表、总数、详情与更新使用同一授权策略。

## 5. 用户反馈入口

### 5.1 入口与资格

助手回答操作栏增加旗帜图标及“反馈错误”。仅当消息已经持久化、有非空回答，且关联运行为 `completed` 或 `partial` 时显示可用入口。运行中、排队中、停止中及 failed/cancelled 的占位或错误消息不开放；运行故障另走运行诊断流程。

旧消息没有 AgentRun 时，可对非空的历史 assistant 消息提交；服务端按同一会话、同一资源版本、严格早于该回答的最近用户消息尝试配对。若时间并列或关联不唯一，返回 422，提示“该历史回复无法可靠关联原问题，暂不支持反馈”，不猜测。后续若需要全面支持旧记录，应先做关联迁移。

### 5.2 提交弹窗

- 标题：“反馈错误”；只读展示问题及回答摘要，支持展开原回答。
- 原因单选：数据/计算错误、回答与问题不符、引用/依据有误、图表/表格有误、其他。
- 补充说明：最多 2,000 字；选“其他”时去除首尾空白后必填，其余可选。
- 提示：“将提交本次问题、回复及相关来源快照给反馈处理人员。请勿填写密码或凭证。”
- 提交中禁用重复点击；成功提示“反馈已提交”，按钮变为“已反馈 · 待处理”。失败保留输入，可重试。
- 本期提交后不编辑、撤回或重复追加；提交者可在原消息处查看待处理/已处理状态。更正反馈诉求作为后续扩展。

### 5.3 去重规则

一名提交者对一条 assistant 消息只创建一条反馈，唯一键为 `(reporter_id, assistant_message_key)`。双击、网络重试和多标签页提交均返回首次记录，不能产生多条处理任务；重复请求中的新原因/说明不覆盖首次内容。不同回答即使问题文字相同也分别建单。

唯一约束兜底：发生并发插入冲突时回滚后查询已有记录，返回 200；新创建返回 201。无需额外引入分布式锁或任务队列。

## 6. 回复校对页面

### 6.1 列表

页标题“回复校对”；说明“此列表为用户标注 AI 回复有误的信息数据”。保留截图列顺序：序号、用户、问题、反馈时间、状态、操作。

| 元素 | 规则 |
| --- | --- |
| 问题搜索 | 按问题快照做大小写不敏感的文字包含匹配，最多 200 字 |
| 用户搜索 | 按提交时用户名快照包含匹配，最多 100 字；本期无真实姓名字段 |
| 状态 | 全部状态（默认）、待处理、已处理 |
| 筛选组合 | 问题、用户、状态之间为 AND；空白字符串视为未设置 |
| 搜索时机 | 300ms 防抖，Enter 立即查询；取消旧请求或忽略过期响应 |
| 默认排序 | `created_at DESC, id DESC`；截图数据未按时间排序，本方案采用最新反馈优先 |
| 分页 | 服务端分页；默认 10，允许 10/20/50，页码从 1 开始 |
| 总数 | 符合当前筛选条件的反馈总数，与列表使用同一条件 |
| 序号 | `(page - 1) × page_size + 行索引 + 1`，不是数据库主键 |
| 用户/问题展示 | 过长截断，支持查看完整文本；用户列保留提交时名称 |
| 状态展示 | 待处理使用橙色，已处理使用青绿色，同时显示文字 |
| 操作 | 保留“处理”；已处理记录仍可打开、补充备注或重新打开 |

搜索值参数化，转义 `%`、`_`，按字面字符包含查询；查询不拼接 SQL。基础版采用 OFFSET 分页，实时插入可能使翻页记录位置变化，刷新后以最新数据为准；大数据量后再评估游标分页/全文索引。

筛选变化重置第 1 页。保存后重新获取当前页与总数；记录因筛选而消失属正常行为。当前页已超出范围时退到最后一个有效页，空集合显示第 1 页。

### 6.2 处理弹窗

桌面宽度建议约 1,080px，最大宽度不超过视口减 48px，高度不超过 85dvh；左右栏约 2:1。窄屏改为单栏，长内容区域可滚动，页脚操作始终可达。复用项目 Dialog、Select、Textarea、Badge 等组件，不复制截图中原生系统下拉菜单的灰色浮层风格。

左栏：

1. 用户提问：只读完整快照；“那上海呢”等追问可展开关联上下文。
2. AI 回复：只读完整回答；支持 Markdown、表格、图表、指标与引用，外框以浅橙色提示“被反馈内容”，不将所有文字染成警告色。
3. 用户反馈：原因、补充说明、反馈时间和用户。
4. 可折叠“来源与上下文”：本次输入的历史问答、模型、业务空间名称/版本、引用片段、实际查询 SQL/参数/结果及截断标识；无相应信息显示“无记录”。

右栏：

1. 处理状态：待处理、已处理，初始化为数据库当前值。
2. 处理备注：0–4,000 字，展示字数；已处理要求去除首尾空白后非空。
3. 最近处理人、最近处理时间；新记录显示“尚未处理”。
4. 可折叠处理历史：按版本显示操作者、时间、状态前后变化及备注变更。

底部“取消”“确认”。确认只在字段合法且有变更时可用；提交中禁用重复操作。关闭、Esc、取消均不保存，有未保存改动时进行弃改确认；点击遮罩不直接关闭。打开后加载详情，不能用列表摘要替代原始回答。

备注示例：“已核对 Q1，统计包含未到期账款；正确口径应为逾期天数 30–60 天，已登记 SQL 修复任务 BUG-123，待回归验证。”判定原回答正确或不属于缺陷时，也需记录核查依据。

### 6.3 页面状态

- 初始加载：表格骨架；查询刷新期间避免旧数据被误认为新结果。
- 无数据：“暂无反馈”；有筛选但无结果：“未找到匹配反馈”，提供清空筛选。
- 详情读取失败：弹窗内提示与重试，不能显示空白回答并允许处理。
- 保存失败：保留草稿并提示重试；网络超时后重新读取版本，辨别是否已经保存。
- 版本冲突：提示“记录已被其他处理人更新，请重新加载后处理”，保留本地备注供复制，不自动覆盖。
- 权限失效：清除管理页敏感缓存，跳转至可访问页面或登录。
- 可访问性：焦点进入/返回弹窗、Tab 顺序、字段标签、状态文字、主题对比度；支持键盘操作和暗色主题。

## 7. 状态与处理规则

```text
提交反馈 → 待处理 ── 核查完成 + 非空备注 ──→ 已处理
             ↑                                │
             └──── 重新打开 + 非空说明 ────────┘
```

| 当前状态 → 目标状态 | 约束与结果 |
| --- | --- |
| 待处理 → 待处理 | 可保存核查中的备注；不视为已完成 |
| 待处理 → 已处理 | 备注必填，记录本次处理人和处理时间 |
| 已处理 → 已处理 | 可修订备注，记录新的操作者/时间及历史 |
| 已处理 → 待处理 | 备注必填，且与当前备注不同，以说明重新打开原因；保留此前历史 |
| 任意 → 相同内容 | 不产生新版本与重复历史，返回当前记录 |

不设置“处理中”、独占领取或实时编辑锁。本期多人处理通过版本冲突避免静默覆盖。前端下拉选择不会立即写库，只有“确认”才在一个事务内保存。

## 8. 数据模型

新增 `answer_feedback`、`answer_feedback_events`；User 新增角色。原始证据与可变处理信息分离，原始快照创建后不可被处理接口覆盖。

### 8.1 answer_feedback

| 字段 | 建议类型 | 说明 |
| --- | --- | --- |
| id | String(36), PK | UUID |
| reporter_id | String(36), FK users | 服务端取当前用户，删除用户时 CASCADE |
| reporter_name_snapshot | String(50) | 提交时用户名，列表搜索与展示使用此值 |
| assistant_message_key | String(36), NOT NULL | 原回答 UUID 的永久副本，用于唯一约束 |
| assistant_message_id / question_message_id | String(36), nullable FK messages | 诊断链接，删除原消息时 SET NULL |
| conversation_id / run_id | String(36), nullable FK | 删除原会话/运行时 SET NULL |
| workspace_id | String(36), nullable | 资源快照标识，不作为跨用户授权范围 |
| question_snapshot | Text, NOT NULL | 原始用户提问，用于列表和搜索 |
| evidence_snapshot | JSON, NOT NULL | 下文定义的问答与来源证据 |
| reason | String(32), NOT NULL | data_error / irrelevant / citation_error / presentation_error / other |
| user_comment | Text | 原始用户说明，默认空字符串 |
| status | String(20), NOT NULL | pending / resolved，默认 pending |
| processing_note | Text | 最新内部处理备注，默认空字符串 |
| last_handled_by | nullable FK users | 最近一次管理更新人，删除操作者时 SET NULL |
| last_handled_at | nullable DateTime | 最近一次管理更新时间，待处理备注更新也会记录 |
| version | Integer, NOT NULL | 初始 1，每次实际处理更新 +1 |
| created_at / updated_at | DateTime | UTC 存储，接口明确输出带 Z 的 ISO 8601 |

约束：唯一 `(reporter_id, assistant_message_key)`；status、reason 用应用枚举与数据库 CHECK 双重约束；version >= 1。索引建议 `(created_at, id)`、`(status, created_at, id)`、`(reporter_id, created_at)`。文本包含查询无法直接利用普通 B-tree 索引，基础版不承诺全文检索规模。

### 8.2 evidence_snapshot v1

由服务端从已授权的持久化消息和 AgentRun 组装，客户端只提交回答 ID、原因和说明：

- `schema_version: 1`。
- `answer`：Message.content、受控的结构化 answer、展示所需图表/指标/查询结果和 citations。
- `context`：运行实际使用的 `input_payload.history`，以及精确的原问题 ID；不复制用户长期记忆。
- `resource`：原运行的 workspace_id、scope_version、kb_ids、source_ids，提交时可获取的名称；名称不是历史配置证明。
- `execution`：model、原运行状态及时间、诊断所需的已存查询 SQL、参数、结果和截断标识。

采用字段白名单，不直接复制整个 input_payload/tool_calls，不保存模型配置、连接串、API Key、授权头、隐藏推理或其他凭证。仅从本次回答已有引用和结果保存证据，不重新查询源数据。

单条快照建议上限 2MiB（UTF-8 序列化后）；超限返回 413 并明确告知未提交成功。本期不静默截断原始回答。原工具结果已被截断时必须保留截断标识，不能宣称获得完整底层数据。该上限在实现前以实际回答样本校准。

### 8.3 answer_feedback_events

字段：`id`、`feedback_id`（CASCADE）、`version`、`action`（created/updated/reopened）、`actor_id`（nullable FK）、`actor_name_snapshot`、`from_status`、`to_status`、`old_note`、`new_note`、`created_at`。唯一 `(feedback_id, version)`。

创建反馈时写入版本 1 的 created 事件；每次实际更新写入对应版本事件。历史只追加，不提供用户编辑/删除 API。操作者删除后使用姓名快照显示“已删除账号”。

### 8.4 生命周期

删除普通会话、消息或业务空间不删除已提交反馈，诊断链接失效时展示“原记录已删除”，核查使用创建时快照。这会使反馈比会话存活更久，需在提交提示和会话删除说明中告知。

建议本期不做自动过期清理、不开放反馈删除；删除提交者账号时，反馈及审计历史随之删除，避免无限保留该账号的问答副本。备份、日志不应额外记录快照正文。组织若需要保留期限或法务留档，需另行确定清理规则及权限；本设计不替业务确定期限。

## 9. 接口契约

统一前缀 `/api`，沿用现有 JWT 认证和 `apiRequest`。普通用户与管理员的响应模型分离，避免内部备注或跨用户证据被过量序列化。

| 方法与路径 | 权限 | 行为 |
| --- | --- | --- |
| POST `/messages/{message_id}/feedback` | 消息所有者 | 创建错误反馈；唯一键已存在则返回首次记录 |
| GET `/sessions/{session_id}/feedback` | 会话所有者 | 返回该会话中自己的反馈摘要，供历史消息恢复，无备注和快照 |
| GET `/feedback` | feedback_admin | 条件搜索和服务端分页 |
| GET `/feedback/{id}` | feedback_admin | 返回完整证据、处理字段及历史 |
| PATCH `/feedback/{id}` | feedback_admin | 原子更新状态/备注，携带 expected_version |

会话反馈摘要按一次请求加载，避免每条消息各发请求；创建后的本地状态同步到摘要缓存。身份切换时清空缓存。

### 9.1 提交

```json
{"reason":"data_error","comment":"金额可能包含未到期账款，请核查统计口径。"}
```

创建响应 201；重复提交响应 200：

```json
{"id":"feedback-uuid","message_id":"assistant-message-uuid","status":"pending","created_at":"2026-10-13T03:00:00Z","deduplicated":false}
```

用户 ID、状态、快照、工作空间、处理人均不可在提交体指定。Pydantic 对未知字段报 422。消息资格、所有权、问题关联与快照校验通过后，同一事务创建记录与事件。

### 9.2 列表与详情

`GET /api/feedback?question=账龄&user=张&status=pending&page=1&page_size=10`。status 省略表示全部；page >= 1，page_size 只能为 10/20/50，非法值返回 422。

```json
{
  "items":[{"id":"feedback-uuid","user":{"id":"user-uuid","name":"张经理"},"question":"本月应收账款账龄","created_at":"2026-10-13T03:00:00Z","status":"pending","version":1}],
  "total":1,"page":1,"page_size":10
}
```

详情包含列表字段、reason、user_comment、evidence_snapshot、processing_note、last_handled_by/at、version、history。列表不返回完整回答和来源快照。时间显示统一使用 Asia/Shanghai，格式 `YYYY/MM/DD HH:mm:ss`；不能将现有无时区 UTC 值直接当成本地时间解析。

### 9.3 保存与并发

```json
{"status":"resolved","processing_note":"已核实账龄区间统计有误，已登记修复任务 BUG-123。","expected_version":1}
```

服务端执行带权限条件和 `WHERE id=:id AND version=:expected_version` 的更新，`version = version + 1`，并在同一事务写入审计事件。匹配不到版本返回 409；不存在返回 404；验证失败返回 422。响应 200 返回最新处理字段和 version。

无变更请求仅在 expected_version 仍匹配时返回 200，不增加版本。网络重试若版本已经变化返回 409，前端重新读取：若最新字段恰好与提交值一致，可显示“已保存”；否则按冲突处理。审计写入失败必须回滚主记录，不能出现状态已变但历史缺失。

## 10. 技术实现建议

采用现有 **React + TypeScript + shadcn/ui / FastAPI + SQLAlchemy + Alembic**，同步事务落库即可；正常提交与处理不调用 LLM，不进入 Agent worker，不增加聊天生成链路耗时。

```text
助手回答 → 反馈提交弹窗 → 普通用户反馈 API → 资格/所有权校验
                                              ↓
                                  反馈快照 + 创建事件（同事务）
                                              ↓
回复校对列表 → 管理员详情 → 人工核查 → 版本校验 + 更新 + 审计（同事务）
```

新增与修改位置：

| 层 | 文件/目录 | 职责 |
| --- | --- | --- |
| 后端模型 | `backend/app/models/feedback.py`、`models/user.py` | 反馈、事件、角色字段 |
| 迁移 | `backend/migrations/versions/` | 使用实施时的下一可用 revision，升级/回退和外键行为 |
| Schema | `backend/app/schemas/feedback.py` | 提交、摘要、列表、详情、更新；限制长度与未知字段 |
| API | `backend/app/api/feedback.py`、`backend/main.py` | 路由、用户/管理员依赖、注册 |
| 服务 | `backend/app/services/feedback_service.py` | 原问题关联、快照白名单、去重、查询与原子更新 |
| 运维 | `backend/scripts/set_feedback_admin.py` | 以 UUID 授权/撤权，明确执行结果 |
| 前端页面 | `frontend/src/components/feedback/` | 列表、提交弹窗、处理弹窗 |
| 前端接入 | `MessageItem.tsx`、`Sidebar.tsx`、`App.tsx` | 反馈入口、菜单、页面切换与会话摘要加载 |
| 前端契约 | `frontend/src/types/feedback.ts`、`services/api.ts` | 类型及接口封装，错误处理 |
| 身份信息 | 后端当前用户响应与 `frontend/src/types/auth.ts` | 增加只读角色/能力，默认无管理权限 |

反馈管理员通过反馈详情读取明确上报的证据，不调用原会话/运行 API 跨用户取数。前端安全渲染 Markdown，禁用任意 HTML/脚本；引用和结果中即使包含操作指令也仅作为证据文本，不执行。现有资源所有权、回答协议和 worker 流程保持原有语义。

容量目标：单实例、10 万条反馈，常用组合筛选与分页 API P95 < 500ms。本机 SQLite 的 10 万条模拟反馈、每场景 20 次进程内 API 测量中，首页 / 组合筛选 / 无结果搜索 / 深分页的 P95 分别为 2.24 / 69.19 / 139.13 / 4.69ms。该测量包含鉴权、查询和响应序列化，不包含网络耗时，不能替代目标部署环境的容量验收。详见 [基准结果](validation/feedback/benchmark.json)。

## 11. 实施顺序与验收

### 11.1 实施顺序

1. 确认第 12 节的权限、备注和生命周期等业务选择。
2. 增加角色、模型和 Alembic 迁移，验证 SQLite/PostgreSQL 外键及历史数据兼容。
3. 实现提交、查询与处理 API，完成权限、事务、去重和并发测试。
4. 接入聊天反馈及历史恢复，再实现截图列表和处理弹窗。
5. 验证真实问答、分页筛选、图表/引用、暗色主题及窄屏，完成回归后再上线。

### 11.2 验收用例

| 类别 | 必须通过的场景 |
| --- | --- |
| 基础闭环 | 提交反馈后列表新增待处理；核查填写备注后变为已处理；刷新仍保留 |
| 截图一致性 | 菜单、六列表格、三种筛选、双栏弹窗、两种处理状态、确认/取消完整可用 |
| 来源配对 | 连续多轮、追问、重新发送和恢复运行均关联对应原问题；不能拿最新问题替代 |
| 回答资格 | 运行中和失败占位不能上报；partial 有正文可上报；旧消息歧义明确失败 |
| 去重 | 连续点击、并发提交、网络重试只生成一条反馈和一个创建事件 |
| 搜索分页 | 条件为 AND；中文和 SQL 通配字符按字面搜索；排序稳定；总数与条件一致 |
| 状态校验 | 已处理空备注拒绝；重新打开需新的说明；无变更保存无新版本 |
| 并发 | A/B 同时打开，A 保存后 B 获得 409，A 的备注不被覆盖，历史不重复 |
| 事务 | 模拟审计写入失败，主记录状态/版本一起回滚 |
| 权限 | 普通用户无法访问管理列表/详情/更新；不能上报他人消息；管理员撤权即时失效 |
| 数据边界 | 前端伪造 reporter、role、snapshot 被拒绝；原会话与文档接口仍禁止跨用户访问 |
| 证据保真 | 金额/单位、图表/表格、引用片段、原查询及截断标记与反馈时结果一致；不混入凭证 |
| 生命周期 | 删除会话/运行后反馈可审核；删除提交者后反馈和事件级联删除；操作者删除保留姓名快照 |
| 失败恢复 | 列表/详情失败可重试；提交失败保留输入；超时重读避免误报保存失败 |
| 交互 | 长问答、2MiB 边界、备注上限、空列表、窄屏、键盘与暗色主题正确 |
| 回归 | 聊天生成、历史恢复、复制/朗读、图表、知识引用、原资源隔离不受影响 |

后端验证重点为归属校验、快照来源、事务和并发；前端验证重点为筛选、保存、冲突及权限交互。仅对固定反馈样本测试不需要真实模型；至少增加一次真实 RAG/SQL 回答的人工端到端核对。实现验收已覆盖以下核心要求，完整结果及环境限制见 [验收记录](validation/feedback.md)。

## 12. 审核重点与建议默认值

本次按以下默认值实施。其中本地管理员指定为 `admin`，已经用户确认。

| 审核项 | 建议默认值 | 影响 |
| --- | --- | --- |
| 管理权限 | 单组织部署，显式授予 feedback_admin，可看当前部署全部上报反馈 | 管理员可接触其他用户提交的业务证据；多组织需另加隔离模型 |
| 功能规模 | 先实现两状态、单条处理 | 与截图一致，暂不提供分派、批量和 SLA |
| 反馈入口 | 显式“反馈错误”及原因，不实现点赞/点踩 | 聚焦错误核查，减少误把偏好评价当缺陷 |
| 完成标准 | 已处理必须有备注；允许带说明重新打开 | 可追溯核查结论，完成不等于自动修复 |
| 备注可见性 | 内部可见，提交者只看状态 | 若需要用户沟通，应新增独立公开回复字段 |
| 数据保留 | 删除会话保留反馈；删除提交者清除反馈；本期无自动清理 | 快照生命周期独立，需要告知用户 |
| 修改原回答 | 不修改，不自动写入知识库/记忆 | 后续修正答案需独立审核和发布流程 |
| 第三方平台 | 本期自建轻量闭环，仅参考公开实践 | 无新增外部服务和业务数据同步 |

## 13. 实施结果

- 已实现独立反馈管理接口、两张持久化表、角色鉴权及 `0008_answer_feedback` 迁移。
- 已接入聊天错误反馈、会话反馈摘要、回复校对列表、处理弹窗、人工处理历史和并发冲突保护。
- 本地 SQLite 数据库已先备份再迁移；原有账号默认保持普通用户，`admin` 经用户确认授予管理权限。
- 自动化结果：后端 148 项通过、2 项 PostgreSQL 集成测试因未配置独立测试库跳过；前端 68 项通过；生产构建通过。
- 浏览器已核对提交、状态保存、列表回写、原始问答/图表/表格、明暗主题及窄屏。额外使用既有真实 SQL 回答的隔离副本核对证据，不新增模型调用。
- PostgreSQL 的实际运行迁移和反馈功能尚未在真实 PostgreSQL 环境验收；现有 Vite 大包体积提示仍存在。
