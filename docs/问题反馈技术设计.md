# 问题反馈技术设计

更新：2026-10-15。本文档阐明智能问数系统中“问题反馈”功能的技术架构、数据结构、状态流转与安全审计机制。该模块旨在提供用户对大模型生成内容及分析证据进行纠错、评价和跟踪的完整闭环，支持对生成事实与证据链条的精准回溯与人工复核。

## 1. 设计目标与核心原则

- **证据不可变性（Evidence Immutability）**：在用户提交反馈时，严格冻结当时的提问快照、模型回答内容、生成所依据的 SQL/指标/中间证据链，即使后续对话或底层数据源被更新或删除，历史反馈仍然保持完好可追溯。
- **状态流转与审计追踪（Audit Trail）**：通过主表记录最新处理状态，附表以追加写入（Append-only）的方式记录每次状态变更、处理批注及操作人，支持完整事件溯源。
- **并发控制（Optimistic Concurrency Control）**：通过整型版本号（Version）实现乐观锁，防止多个运营/管理员在并发审核时发生数据覆盖。
- **提交幂等与去重**：同一用户针对同一条助手消息仅允许提交一条有效反馈，避免网络重试或用户重复点击导致垃圾记录堆积。

## 2. 总体架构与数据流

```text
[ 前端界面 (Chat UI) ]
   │
   ├─ 用户点击回答下方「反馈」按钮 (赞同/踩)
   │  └─ 携带: assistant_message_key, question, evidence, reason, comment
   ▼
[ API 层 (app/api/feedback.py) ]
   │
   ├─ 1. 用户身份鉴权与租户校验
   ├─ 2. 检查 (reporter_id, assistant_message_key) 唯一性
   ├─ 3. 持久化至 AnswerFeedback 与 AnswerFeedbackEvent (事务提交)
   ▼
[ 管理/运营审核 (Admin Review) ]
   │
   ├─ 查询列表 (按状态过滤、按时间倒序)
   ├─ 更新处理状态: pending -> resolved，录入 processing_note
   └─ 乐观锁校验 (version 匹配则自增，并追加事件审计)
```

## 3. 数据模型设计

该功能由 `app/models/feedback.py` 定义两个核心实体：`AnswerFeedback`（反馈主表）与 `AnswerFeedbackEvent`（流转事件历史表）。

### 3.1 主表：answer_feedback

| 字段名 | 类型 | 说明 | 约束 |
| :--- | :--- | :--- | :--- |
| `id` | `VARCHAR(36)` | 反馈主键 UUID | PK |
| `reporter_id` | `VARCHAR(36)` | 提交人用户 ID | FK -> `users.id` (CASCADE) |
| `reporter_name_snapshot` | `VARCHAR(50)` | 提交人当时显示名称快照 | NOT NULL |
| `assistant_message_key` | `VARCHAR(36)` | 助手消息的客户端唯一标识 | NOT NULL |
| `assistant_message_id` | `VARCHAR(36)` | 关联的数据库消息记录 ID | FK -> `messages.id` (SET NULL) |
| `question_message_id` | `VARCHAR(36)` | 对应用户提问的消息记录 ID | FK -> `messages.id` (SET NULL) |
| `conversation_id` | `VARCHAR(36)` | 所属会话 ID | FK -> `conversations.id` (SET NULL) |
| `run_id` | `VARCHAR(36)` | 关联的 Agent 运行任务 ID | FK -> `agent_runs.id` (SET NULL) |
| `workspace_id` | `VARCHAR(36)` | 所属业务空间 ID | 可空 |
| `question_snapshot` | `TEXT` | 用户原始提问快照 | NOT NULL |
| `evidence_snapshot` | `JSON` | 包含图表配置、SQL 查询、指标计算及引用来源的不可变证据快照 | NOT NULL |
| `reason` | `VARCHAR(32)` | 反馈原因分类 | 枚举值检查约束 |
| `user_comment` | `TEXT` | 用户详细文本反馈描述 | 默认空字符串 |
| `status` | `VARCHAR(20)` | 处理状态 | 默认 `'pending'`，支持 `'pending'`, `'resolved'` |
| `processing_note` | `TEXT` | 运营审核人员填写的处理结果说明 | 默认空字符串 |
| `last_handled_by` | `VARCHAR(36)` | 最近一次处理人 ID | FK -> `users.id` (SET NULL) |
| `last_handled_at` | `DATETIME` | 最近一次处理时间 | 可空 |
| `version` | `INTEGER` | 乐观锁版本号，每次流转递增 | 默认 1，检查约束 `>= 1` |
| `created_at` | `DATETIME` | 创建时间 (UTC) | 默认当前时间 |
| `updated_at` | `DATETIME` | 更新时间 (UTC) | 默认当前时间 |

#### 关键约束与索引

- **防重唯一约束**：`UNIQUE (reporter_id, assistant_message_key)`，彻底杜绝重复提交。
- **状态枚举约束**：`CHECK (status IN ('pending', 'resolved'))`。
- **原因枚举约束**：`CHECK (reason IN ('data_error', 'irrelevant', 'citation_error', 'presentation_error', 'other'))`：
  - `data_error`: 数据计算错误或统计口径有误。
  - `irrelevant`: 答非所问或脱离用户意图。
  - `citation_error`: 引用事实或引用源标记错误。
  - `presentation_error`: 图表格式、格式排版或显示异常。
  - `other`: 其它问题。
- **查询索引**：
  - `(created_at, id)`：全局时间倒序游标分页。
  - `(status, created_at, id)`：按待处理/已解决分类的高效索引。
  - `(reporter_id, created_at)`：个人反馈历史检索。

### 3.2 历史审计表：answer_feedback_events

| 字段名 | 类型 | 说明 | 约束 |
| :--- | :--- | :--- | :--- |
| `id` | `VARCHAR(36)` | 事件记录 UUID | PK |
| `feedback_id` | `VARCHAR(36)` | 关联的反馈 ID | FK -> `answer_feedback.id` (CASCADE) |
| `version` | `INTEGER` | 对应版本号 | NOT NULL，联合唯一 `(feedback_id, version)` |
| `action` | `VARCHAR(20)` | 动作（如 `'created'`, `'resolved'`, `'reopened'`, `'commented'`） | NOT NULL |
| `actor_id` | `VARCHAR(36)` | 操作人 ID | FK -> `users.id` (SET NULL) |
| `actor_name_snapshot` | `VARCHAR(50)` | 操作人当时名称快照 | NOT NULL |
| `from_status` | `VARCHAR(20)` | 变更前状态 | 可空（创建时为空） |
| `to_status` | `VARCHAR(20)` | 变更后状态 | NOT NULL |
| `old_note` | `TEXT` | 变更前处理批注 | 默认空字符串 |
| `new_note` | `TEXT` | 变更后处理批注 | 默认空字符串 |
| `created_at` | `DATETIME` | 事件触发时间 (UTC) | 默认当前时间 |

## 4. 接口与交互契约

### 4.1 提交问题反馈

- **路径**：`POST /feedback`
- **权限**：登录用户
- **请求体（JSON）**：

```json
{
  "assistant_message_key": "msg-uuid-or-client-id",
  "assistant_message_id": "optional-db-message-id",
  "question_message_id": "optional-db-question-id",
  "conversation_id": "conv-uuid",
  "run_id": "run-uuid",
  "workspace_id": "workspace-uuid",
  "question_snapshot": "查询近30天华东区销售总额",
  "evidence_snapshot": {
    "sql": "SELECT SUM(amount) FROM sales_orders WHERE region = '华东区' AND order_date >= '2026-09-15'",
    "data_preview": [{"sum": 1285000}],
    "sources": ["ds-orders-2026"]
  },
  "reason": "data_error",
  "user_comment": "未剔除已退款订单，实际销售额应为 112 万元"
}
```

- **响应**：HTTP 201，返回创建成功的 `AnswerFeedback` 对象详情。
- **错误场景**：若已存在相同 `(reporter_id, assistant_message_key)`，返回 HTTP 409 Conflict。

### 4.2 审核/处理反馈

- **路径**：`PUT /feedback/{id}`
- **权限**：管理员或运营人员
- **请求体（JSON）**：

```json
{
  "version": 1,
  "status": "resolved",
  "processing_note": "已在指标定义中补充 status != 'refunded' 过滤规则，口径已更新。"
}
```

- **处理逻辑**：
  1. 开启事务，根据 `id` 读取当前记录并校验 `version == payload.version`。若不一致抛出 HTTP 409（提示：“记录已被其他人更新，请刷新重试”）。
  2. 执行 `UPDATE answer_feedback SET status = :status, processing_note = :note, version = version + 1, last_handled_by = :user_id, last_handled_at = :now WHERE id = :id AND version = :version`。
  3. 写入一条 `AnswerFeedbackEvent`，记录版本变化与状态迁移。
  4. 提交事务。

### 4.3 列表与事件追溯

- `GET /feedback?status=pending&limit=20`：支持按状态、时间游标分页检索。
- `GET /feedback/{id}/events`：按 `version ASC` 返回该条反馈的全生命周期审计日志。

## 5. 边界保护与容错机制

1. **外键级联保护**：消息记录和会话可能因定期归档或用户清理被删除，外键配置 `ondelete='SET NULL'`，确保即便关联的会话或消息物理删除，反馈记录与证据快照仍然永久保留，不受业务消息生命周期影响。
2. **证据快照大小限制**：在 API 入口对 `evidence_snapshot` 限制最大存储量（如 1MB），防止过大二进制或海量预览数据溢出导致数据库性能恶化。
3. **敏感信息脱敏**：证据快照中的敏感数据库凭证、用户鉴权 Token 在存入快照前由后端拦截并清除。
